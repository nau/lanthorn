## Token refresh

*Informative.* A client trades a refresh token for a new access token and a new refresh token. Each refresh token works once, because the auth service revokes it during the trade. A second use of a revoked refresh token means that someone copied it, so the auth service revokes every refresh token in that family.

**Who:** The client that holds a refresh token.

**Trigger:** The client presents a refresh token to the auth service.

**Structure:**

| Direction | Field | Type |
|---|---|---|
| Input | refresh token | opaque string |
| Output | access token | string |
| Output | new refresh token | opaque string |

A *token family* is the set of all refresh tokens that descend from one initial sign-in.

**Checks enforced here:**

- The auth service MUST issue a new refresh token on every successful refresh. `[TR-1]`
- The auth service MUST revoke the presented refresh token before it returns the new refresh token. `[TR-2]`
- The auth service MUST revoke the whole token family when a client presents an already revoked refresh token. `[TR-3]`

*Example, illustrative.* A family starts with refresh token R1.

| Step | Client presents | Result | State after |
|---|---|---|---|
| 1 | R1 | accept, issue R2 | R1 revoked, R2 valid |
| 2 | R1 again | reject, revoke family | R1 and R2 revoked |
| 3 | R2 | reject | R1 and R2 revoked |

**Why:** `[TR-1]` and `[TR-2]` together make a stolen refresh token single-use. `[TR-3]` turns the replay of a stolen token into a detected theft rather than a single rejected request. Without `[TR-3]`, the thief or the client can keep a valid token, and the theft stays invisible. In step 3, the client loses R2 on purpose, so the user must sign in again.

**Checks delegated elsewhere:** None.
