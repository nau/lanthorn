# Decision: grace period for a reused refresh token

## Overview

*Informative.* A client sometimes sends a refresh token twice. Usually the first response was lost, so the client retries with the same token. The auth service revokes a refresh token when it is used, so the retry looks like a stolen token. A stolen token would make the auth service revoke the whole token family. To tell the two cases apart, the auth service accepts a reused refresh token for 10 seconds after the revocation, and treats a later reuse as theft. Clients need no change, because they send the same request as before.

## Goals and non-goals

*Informative.*

**Goals**

- Stop the auth service from revoking a token family when a client retries after a lost response.
- Keep the detection of a stolen refresh token.
- Require no change in any client.

**Non-goals**

- Exact separation of a retry from a replay. The grace period cannot do this.
- A per-client retry token.
- A change to any client.

## Approaches

*Informative.*

**Grace period of 10 seconds (chosen).** The auth service tolerates a reused refresh token for 10 seconds after the revocation.

- Trade-off: it is not exact. A reuse inside the grace period is treated as a retry, even if a thief sent it.
- Why it won: it needs no client change.

**Per-client retry token (rejected).** Each client sends a retry token that marks a request as a retry of an earlier one.

- Trade-off: it is exact, but every client must change.
- Why it lost: the cost of changing every client is higher than the loss of exactness.

## Assumptions

None.

## Definitions

- **Refresh token**: the credential that a client trades for a new access token and a new refresh token.
- **Token family**: all refresh tokens that descend from one original refresh token.
- **Grace period**: the 10 seconds that start when the auth service revokes a refresh token.
- **Reuse**: a client presents a refresh token that the auth service has already revoked.

## Reuse of a refresh token

**Overview.** *Informative.* A client presents a revoked refresh token. If the grace period is still running, the auth service treats the request as a retry and does not revoke the family. If the grace period has ended, the auth service treats the request as theft and revokes the whole token family.

**Who.** A client that presents a refresh token.

**Trigger.** The presented refresh token is already revoked.

**Structure.**

| Field | Direction | Type | Note |
|---|---|---|---|
| Refresh token | Input | Opaque string | Same input as an ordinary refresh |
| Grace period | Configuration | Seconds | 10 |
| Family revocation | Output | Event | Only after the grace period ends |

**Checks enforced here.**

- The auth service MUST NOT revoke the token family when a reuse arrives inside the grace period. `[RG-1]`
- The auth service MUST revoke the token family when a reuse arrives after the grace period has ended. `[RG-2]`
- The auth service MUST NOT require a client to send any input other than the refresh token. `[RG-3]`

*Example, illustrative.* A refresh token is revoked at server time `T`.

| Reuse arrives at | Result |
|---|---|
| `T` + 4 seconds | no family revocation |
| `T` + 30 seconds | family revoked |

The case of a reuse at exactly `T` + 10 seconds is open. See Open questions.

**Why:** `[RG-1]` stops a lost response from logging out a legitimate client. `[RG-2]` keeps the detection of a stolen token, which makes a late replay visible. `[RG-3]` is the reason this approach was chosen, because it keeps every existing client working. Inside the grace period a thief is indistinguishable from a retrying client. That is the cost of the choice.

**Checks delegated elsewhere.** None.

## Open questions

*Informative.*

- Does a reuse at exactly 10 seconds after the revocation count as inside the grace period? Open.
- What does the auth service return for a reuse inside the grace period? For example, it could issue new tokens or return the earlier ones. Open.
