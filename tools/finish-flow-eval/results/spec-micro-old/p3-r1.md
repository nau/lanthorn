## Token refresh

- The token service MUST issue a new refresh token on every refresh. `[TR-1]`
- The token service MUST revoke the presented refresh token before it returns the new one. `[TR-2]`
- The token service MUST revoke the whole family on reuse of a revoked token. `[TR-3]`
- The token service MUST reject a refresh token that was issued more than 30 days before the time of the request. `[TR-4]`

*Example, illustrative, for `[TR-4]`.* A refresh token is issued at `1700000000`. Thirty days is 2,592,000 seconds, so the limit is `1702592000`.

| Request time | Result |
|---|---|
| 1702591999 | accept |
| 1702592000 | accept, the token is exactly 30 days old, not older |
| 1702592001 | reject |

Notes:

- I added the rule as `[TR-4]` at the end and did not renumber, because published IDs are frozen. I assumed `[TR-1]` to `[TR-3]` are published. If they are still draft, you can move it to the position you prefer.
- "Older than 30 days" is ambiguous at the boundary, so I chose that exactly 30 days is accepted. I also measured age from the issue time of the refresh token. Please confirm both choices.
- I did not write a "Why" note, because I don't know your rationale. Add one if you have it.
- Open point: the rule does not say whether a rejection for age also revokes the token family. If it should, that needs its own numbered rule.
